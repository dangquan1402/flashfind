# Benchmark results

Generated by `bench/run.sh`. Engines are measured **in-process** through their libraries (flashfind `Session::search`; fsearch `query::Searcher::search` on a `live::Live` over an index built by `walk::scan` + `Index::build` for the same root). Latency includes query parsing and turning the top 50 hits into paths. Synthetic tree, warm page cache. Each engine ran twice, alternating; the better run (lower crawl time / lower overall p50) is shown for each.

## Notes

- Both engines run in-process on the same machine, tree, query file and `limit` (50). fsearch is driven through its library (`walk::scan` → `Index::build` → `Index::load` → `live::Live` → `query::Searcher::search`) because its daemon always indexes `/`; this measures its engine, not its socket/CLI round trip (which only adds to fsearch's numbers).
- Synthetic tree, warm metadata cache (a warm-up crawl runs first). Real disks have a different name distribution (more duplicate names, deeper system trees); treat these as engine comparisons, not whole-disk predictions.
- `hit@1` uses flashfind's own generator, so read it as a sanity check rather than an independent quality benchmark. fsearch, by design, does not forgive a typo in the first character (`typo_first`) or a 4-letter-or-shorter typo.
- `keys` replays typing each target name one character at a time in one search session; both engines narrow from the previous keystroke (fsearch via its name cache, flashfind via `Session`).
